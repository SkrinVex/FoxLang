# Измерение графики Skrumi на Android

Raycaster рисует программно в C++ и передаёт полный кадр в `FoxView`. Путь кадра:
RGB-буфер → преобразование в ARGB и Java `int[]` через JNI → `Bitmap.setPixels()`
→ `Canvas.drawBitmap()`. Это несколько проходов по памяти; при увеличении
разрешения их стоимость растёт. FPS игры включает ещё VM, расчёт лучей, рисование
примитивов и ожидание в `window_poll()`, поэтому одного FPS для оценки JNI мало.

## Записать измерение

Установите [APK raycaster](ANDROID.md#демо-лабиринт-в-псевдо-3d), подключите телефон
с USB-отладкой или запустите эмулятор. Разблокируйте экран и выполните из репозитория:

```bash
python3 packaging/profile_android.py --output build/android-profile
```

Нужен `adb` из Android SDK в `PATH` (или `--adb /путь/к/adb`). Если устройств несколько,
укажите `--serial SERIAL`. Скрипт заново запускает игру, ждёт 5 секунд прогрева,
затем собирает 10 секунд системной трассы. `--warmup` и `--seconds` меняют интервалы.
В течение записи можно двигаться экранными кнопками и поворачивать устройство.
Нужен APK с включённой отладкой: демо из релиза и обычная сборка Gradle подходят.
Одна запись использует общий буфер `atrace` выбранного устройства.

Результаты:

- `summary.json`: число замеров, среднее, медиана, p95 и максимум по этапам;
- `trace.txt`: полная текстовая трасса Android для подробного разбора;
- `device.json`: модель, версии Android и APK, ABI, признак эмулятора, размер/плотность экрана;
- `memory-before.txt`, `memory-after.txt`: `dumpsys meminfo` процесса до/после записи.

Повторно разобрать сохранённую трассу без устройства:

```bash
python3 packaging/profile_android.py --trace build/android-profile/trace.txt
```

Отсутствующие маркеры вызывают ошибку, а не превращаются в нулевое время кадра.
Незавершённые секции на границе записи исключаются из статистики. Маркеры также
видны в Android Studio System Trace / Perfetto при включённой трассировке приложения.
Без трассировки приложение не собирает статистику кадров и не пишет эти события.

## Что именно измеряется

| Секция | Граница измерения |
|---|---|
| `FoxLang.present WIDTHxHEIGHT` | Нативный вызов Host: подготовка кадра, JNI, callback `onFrame()` и освобождение локальной JNI-ссылки. Исполнение VM и построение сцены сюда не входят |
| `FoxLang.frame.copy` | Выделение Java-массива и временного C++-буфера, преобразование RGB → ARGB, `SetIntArrayRegion`, освобождение временного буфера |
| `FoxView.upload` | Ожидание блокировки кадра, создание Bitmap при смене размера и `Bitmap.setPixels()` |
| `FoxView.draw` | Вызов рисования на UI-потоке, включая ожидание блокировки и передачу команд Canvas |

Все значения — **прошедшее время**, включая вытеснение потока планировщиком.
`copy` и `upload` входят в `present`: складывать все три величины нельзя.
Числа кадров и вызовов `draw` могут отличаться: Android объединяет обновления
экрана и может перерисовать один кадр несколько раз. `frames_by_size` показывает
число завершённых передач каждого разрешения; статистика этапов суммарная.
Для сравнения разрешений делайте отдельные записи без поворота во время замера.

`draw` **не измеряет завершение работы GPU или задержку до появления картинки**:
при аппаратном Canvas это время подготовки команд. Для этих вопросов нужна
системная трасса с FrameTimeline/SurfaceFlinger/GPU на поддерживаемом устройстве.
Два снимка памяти помогают увидеть изменение PSS, но сами по себе не доказывают
отсутствие утечек; для этого нужны длительные прогоны и профилирование аллокаций.

## CI и настоящий телефон

Workflow Android сохраняет отчёты и трассы в артефактах `android-tests-…-api-28/35`.
Перед записью выполняются тесты runtime и жизненного цикла raycaster. Сборочный
job отдельно проверяет четыре ABI и выравнивание ELF/APK для 16-КБ страниц.

Измерения CI выполняются на **эмуляторах x86_64**. Они проверяют работоспособность
инструмента измерения и показывают стоимость на конкретном эмуляторе; это не
обещание FPS на ARM-телефоне. Сравнивайте записи на одном устройстве, с одним
разрешением, сборкой и режимом питания. Порогов производительности, зависящих от
нагрузки общего CI runner, в тестах нет. Оптимизацию копирования или переход на
другой способ вывода стоит выбирать по профилю целевого устройства.
